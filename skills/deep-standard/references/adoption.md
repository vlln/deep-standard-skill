# 装进项目

把体系装进项目分三步：**判定档位 → 生成分层计划并逐项授权 → 执行并落档**。不要一次性铺开全部六条法则；不要在未获授权时改动现有文件。

## 第一步：判定档位

档位不是主观选择，按下表的客观信号判定，拿不准时向人类提问并附建议档位与理由。

| 信号 | L1 | L2 | L3 |
|------|----|----|----|
| 预期寿命 | 一个月以上 | 持续维护 | 长期维护 |
| CI | 可以没有 | 有 | 有，且分组/多 job |
| 协作者（含 agent） | 1 | 2 以上 | 多，且并行改动 |
| 外部消费者（被别的项目依赖/发布制品） | 无 | 有或计划有 | 有 |
| 契约面数量（公开接口、on-disk 格式、wire 协议、配置格式、模型/用户可见输出） | 0–1 | 2–4 | 5 以上 |
| 生成物（生成的文档、目录、代码） | 无 | 有 | 有多个 |

取**多数信号命中的最低档**。低档不是"简陋版"——它是与项目规模匹配的正确形态。**升档是一个独立的、被记录的决定**（写一条决策记录），不是随手加脚本。

同时判定并写下**阶段取舍档案**（元法则 B）：当前阶段在"基础正确性"与"兼容性/稳定性"之间站哪一边，以及**这个站位何时失效**。典型写法见 [assets/templates/AGENTS.md](../assets/templates/AGENTS.md) 的对应小节。

## 第二步：扫描并生成分层计划

先扫描，产出事实，再谈动作。**扫描阶段不改任何文件。**

扫描对象：

- 根目录常驻文件：`AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`、`README.md`，以及其他 agent 指令文件
- 已有的决策文档：`docs/adr/`、`docs/rfc/`、`design/`、散落在 `docs/` 的设计文档
- 已有的检查：CI 配置、git hook 配置、lint 配置、`scripts/` 下的校验脚本、package 脚本里的 `check:*` / `verify:*`
- 已有的测试：目录结构、测试框架、覆盖率配置、快照/fixture 目录
- 生成物：搜索 `generated`、`autogenerated`、"DO NOT EDIT" 标记
- 技术栈与包结构（用于决定门禁用什么语言写、装在哪里）

然后生成**分层计划表**，每项标注动作类型：

| 动作 | 含义 |
|------|------|
| 新建 | 项目没有对应物，从模板实例化 |
| 合并 | 已有文件，在其中追加本体系需要的小节，保留原有内容 |
| 改造 | 已有内容语义对应，但形态不符（如 ADR 没有备选方案段、没有生命周期目录），转换后移入 |
| 保留并引用 | 已有内容形态不同但有效，不动它，在常驻文件里链接 |
| 跳过 | 已满足 |

计划表示例：

```
| 目标 | 动作 | 说明 |
|------|------|------|
| AGENTS.md | 合并 | 已存在。追加：阶段取舍档案、规则分层导航、门禁命令表 |
| docs/adr/ → decisions/ | 改造 | 现有 12 份 ADR：补生命周期目录（implemented/ 为主）、补分类、补备选方案段（不可考的标注"未记录"） |
| decisions/README.md | 新建 | 记录契约（生命周期、分类封闭集、骨架、取代规则） |
| scripts/verify-md-links.* | 新建 | L1 唯一门禁：相对链接可达性 |
| .github/workflows/ci.yml | 合并 | 追加门禁 job；现有 test job 保留 |
| lefthook/husky 配置 | 改造 | 现有 pre-commit 跑全量测试 → 收窄为暂存区 lint + 格式，测试交给 CI |
| docs/ARCHITECTURE.md | 保留并引用 | 已有且有效，在 AGENTS.md 中链接为"改动前必读" |
| 覆盖率门禁 | 跳过 | L2 项目，本档不装 |
```

**逐项呈现给人类授权**，每项可同意 / 修改 / 拒绝。被拒绝的项记下来，别在下次悄悄再装一遍。

## 第三步：执行并落档

按授权后的计划执行，顺序有讲究：

1. **先落常驻文件**（法则 1）：它是后续一切的导航入口。此时不设字数上限。
2. **再落决策记录契约**（法则 3），并把"装入本体系"这件事本身写成第一条决策记录——记录选定的档位、判定依据、被拒绝的项，以及升档的触发条件。这条记录是后续审计的锚点。
3. **再落第一个门禁**（法则 2）：从**文档相对链接可达性**开始。它便宜、语言中立、立刻能抓到真问题，且能验证整条门禁通路（编排器、CI 接线、自证测试）是否打通。
4. **收窄 hook**（法则 4）：把跑全量测试的 pre-commit / pre-push 收窄。这一步经常遭到抵触，理由要讲清楚：慢 hook 会被 `--no-verify` 绕过，绕过一次就永远失效；窄而必过的 hook 才是真防线。
5. **其余项按计划执行**，每装一个门禁都要连带它的自证测试（见 [gates-as-code.md](gates-as-code.md)）。

执行完成的判据：常驻文件里的每一条规则都能链接到它的家；每个门禁都能在本地一条命令跑起来并**故意制造一次违规验证它会失败**；第一条决策记录已提交。

## 现有项目的两条原则

**合并优先，隔离兜底。** 尽最大努力把现有内容融进本体系，而不是另起炉灶再让两套并存。已有的 ADR 目录改造成生命周期目录，而不是新建一个平行的 `decisions/`；已有的 `CONTRIBUTING.md` 追加小节，而不是让规则分裂到两个文件。只有在现有形态确实无法承载时才隔离新建，并在两边互链。

**不要为了体系完整而制造空壳。** 没有生成物就不要装生成物门禁；没有外部消费者就不要装发布产物冒烟。空壳门禁永远不会失败，只会训练所有人忽略门禁输出。缺失的能力写进决策记录的"何时需要"，而不是先建一个占位符。

## 审计现有项目

如果任务是"审计现有工程规范"而不是"装进去"，用六条法则当审计轴，每条问同一组问题：

1. 这条法则对应的机制在项目里存在吗？
2. 如果存在，它是**可执行的**还是只是散文？谁会拒绝违规？
3. 如果有门禁，它**自证过吗**？故意造一个违规，它会失败吗？
4. 有没有**多个家**（同一条规则出现在多处）？搜索特征短语。
5. 有没有**空壳**（存在但从不可能失败）？

产出格式：每条法则一行结论 + 依据 + 证据路径（命令输出、文件路径、行号）。**只有结论没有依据的审计项视为未完成**（见 SKILL.md 反模式）。审计不改文件；修复建议按上面的分层计划表格式给出，等授权。
