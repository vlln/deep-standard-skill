# 决策记录

## 它是什么，不是什么

决策记录是**由改动者（含 agent）写的 RFC**：记录一个决策或提案的**动机、决定、被击败的备选方案、后果、验证契约**——代码和普通文档承载不了的那部分。

它**不是**：任务清单、迁移计划的长期归属、变更日志、状态看板。也**不是**圣经：它记录当时的判断，不是不可推翻的真理（元法则 A）。

## 生命周期即路径

路径形如 `{生命周期}/{分类}/yyyy-mm-dd-主题标题.md`，两个维度都编码在路径里：

**生命周期**（顶层目录，记录随状态变化在目录间移动）：

| 目录 | 含义 |
|------|------|
| `proposed/` | 实施前被评审的提案；尚未建成或只建了一部分 |
| `implemented/` | 决策已落地。文件记录决定了什么、否决了什么，并**与实际落地的形态保持同步** |
| `rejected/` | 提案被考虑后否决。**仅在其理由仍能阻止一个有诱惑力的错误时保留**，否则删除 |
| `archived/` | 已实施且理由不再可能指导未来工作的记录。**永久冻结** |

**分类**（嵌套目录）取自一个**封闭集合**，由门禁校验；加分类必须同时改集合定义与契约文档。一套通用的分类：

| 分类 | 覆盖 |
|------|------|
| `feature` | 新增的用户可见能力 |
| `bug-fix` | 修正缺陷，或补上事故复盘暴露的缺口 |
| `simplification` | 删除代码、行为或表面积，不新增能力 |
| `architecture` | 关于**发布出去的源码**的结构性决策：模块如何关联、运行时词汇是什么 |
| `process` | 代码**周边**的工具、策略、流程：门禁、包管理器、依赖引入——不是运行时行为 |
| `testing` | 测试基建与策略 |

`architecture` 与 `process` 的界线：**architecture 关于我们发布的源码，process 关于围绕它的工具与流程**。刻意不设 `refactor`——它与 `simplification` 重叠，而后者的判据"可观察行为是否改变"已经覆盖。

文件名里的日期是该主题**首次被提出**的日期（按版本历史），不是实施日期。记录之间的互相引用**用相对路径链接**，绝不用纯散文描述或编号——链接可被门禁机械校验，且在目录间移动后仍可修复。

**不要建集中索引文件。** 活跃的生命周期树本身就是清单：浏览目录或全仓库搜索。索引文件是又一个会漂移的手抄清单。

## 什么时候必须写

**每个非平凡改动必须在同一个 PR 内新增或更新至少一条记录。** 非平凡的判据：改变了行为、架构、跨文件或跨模块的契约、流程或工具、测试策略、on-disk/wire/配置格式，或任何维护者日后可能重新审视的决策。

- 更新**已经拥有该决策**的那条记录即满足要求；**不要造重复件**。
- 只有纯机械的、局部的、无行为/契约/结构/流程/理由变化的编辑豁免。
- 面向未来的大块工作从 `proposed/` 起步；已经做出的决策直接从 `implemented/` 起步。
- 编辑 `implemented/` 记录以跟踪其决策**当前落在哪里**（文件移动、重命名、键名或默认值变化）是**要求**，不是禁止。改的是事实，不是决策。
- 一条记录**永远不会被改成另一个决策**：用新记录取代它，两条互链。

## 文件骨架

三行头部固定：

```markdown
# Decision: <标题>

Status: <状态>
```

`Status:` 的值与所在生命周期目录**必须一致**，由门禁交叉校验：`proposed` / `implemented` / `rejected — <一行原因>`。状态行不带日期、不带括注——文件名承载首次提出的日期，版本历史承载其余一切。被否决的记录是唯一在状态行里带内容的，因为"结论"正是读者来看的东西。

正文一律以 `## Problem`（问题/动机，**写成脱离解决方案也能读懂**）开头。之后按生命周期不同：

`proposed/`：
```markdown
## Problem
## Proposal
…按需的专门技术章节…
## Alternatives considered
## Acceptance criteria
## Risks
```

`implemented/`：
```markdown
## Problem
## Decision
…按需的专门技术章节…
## Alternatives considered
## Consequences
```

- `## Proposal` 可以用将来时态——计划、迁移步骤、待决问题在未建成时属于这里。
- `## Decision` 用**现在时**描述已落地的现实，全文与之保持同步。
- `## Consequences` 记录这个取舍**付出了什么，也换到了什么**。
- **提案期的标题在已实施记录里是规划语气，门禁应当拒绝**：`## Proposal`、`## Plan`、`## Migration plan`、`## Acceptance criteria` 不得出现在 `implemented/` 记录里。`## Testing` / `## Deferred` / `## Related` 只要写的是现在时事实就没问题。
- `rejected/` 记录是被冻结的提案：保留它提案期的章节，结论在状态行。

被机械校验的结构标记（`# Decision: `、`Status:`、章节标题、分类目录名）**保持英文**，正文语言随项目。这样门禁与工具链语言中立。

## 备选方案：强制

**每条记录都必须有 `## Alternatives considered`**：每个真实存在过的备选方案及它为何落败——一个方案一段（加粗开头），有争议的用 `### 为什么不用 <X>?` 子节。

**记录一个决策却不记它击败了什么，等于邀请日后重新扯皮**——而这正是决策记录存在要防止的失败模式。

备选方案**只能记录，不能编造**。历史遗留的记录若其备选方案无法从任何记录中重建，用一个固定的机器可识别标记声明，并让门禁**仅对该标记之前的旧文件**接受：

```markdown
<!-- decision-format: alternatives-not-recorded (pre-format record) -->
```

## 取代检查

**每条新记录都触发一次取代检查**：搜索活跃树里覆盖同一决策或机制的旧记录，分类为：

- **完全取代**：旧记录的每一条独有理由、备选方案、后果、验证契约都已被新记录承载 → 在同一个 PR 里归档旧记录。
- **部分取代**：旧记录仍有独有内容 → **保持活跃并互链**，把仍然有效的事实更新到位。

删除一个方向、一种默认值、一个实现、一种呈现，都属于**部分**取代；任何残留的持久化数据或兼容处理同样属于部分取代。

## 归档与删除

**归档判据**：已实施、决策完整、且其理由**不太可能指导未来工作**。反之，只要它的备选方案、所有权边界、否定性保证、持久化/wire 语义、安全规则、或"什么条件下应当重新引入"仍然有用，就**保持活跃**。

- **绝不归档提案**：过时的提案要么否决，要么更新。
- 被否决的记录只在它还能阻止一个**似乎有道理的**错误时保留，否则连同其全部关联文件一起删除。
- **判据是语义，不是字数、年龄或配额。** 字数与年龄只是发现线索。

**归档动作**：把该记录的全部关联文件（正文、译文、一致性记录等）一起移入 `archived/{分类}/`，保留 `Status: implemented`，在状态行下方插入一行 `Archived: YYYY-MM-DD`，修复或删除指向它的入站链接。**这是归档过程中唯一允许的内容改动。**

**封存即永久冻结**：此后不得编辑、翻译、重排、更新、移动、删除，也不得当作当前行为的依据。文档门禁**跳过**归档内容（包括它的出站链接）；活跃散文在有意引用历史时仍可链接进去。用**内容哈希清单**（只追加）守护冻结状态，由门禁校验封闭的分类树、完整的关联文件、归档元数据、哈希一致性。

## 合并删除（consolidation）

一条被**完全**取代的已实施记录，可以合并进当前拥有该决策的记录后删除。删除前，接收方必须保住：每一条独有理由、备选方案、后果、验证契约、以及**已命名的覆盖缺口**；修好全部入站链接；同一个 PR 内删除其全部关联文件。

- 部分取代**不符合条件**：两条都保持活跃并互链。
- 合并**不得**把旧文件改写成它的反面，也**不得**依赖版本历史作为理由的唯一副本。
- 一条"新增能力"的记录只有在该能力已从生产代码、配置、schema、持久化/wire 格式、迁移与兼容行为中**完全消失**，且没有任何现行文档把它呈现为可用、没有任何测试把它当作受支持行为时，才可合并进后来的"移除"记录。移除方必须保住原始动机、为何它不再值得、除完全移除外的备选方案、放弃了什么能力、重新引入的条件、以及完全消失的验证证据。过时的实现清单和只验证被删行为的测试**不算**当前验证契约。
