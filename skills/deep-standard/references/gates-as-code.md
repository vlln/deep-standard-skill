# 门禁即代码

本文件规定**门禁契约**：一个门禁要满足什么才算合格，以及它的编排、自证、生成物防漂移规则。这里不提供现成脚本——门禁必须用项目自己的技术栈写，用项目自己的方式跑；照抄的脚本会成为第二套没人维护的基建。

## 门禁契约

一个合格的门禁满足全部七条：

1. **只拒绝一条不变量。** 一个门禁一件事。做两件事的门禁在其中一件失败时给出误导性的定位，且无法被单独豁免或单独自证。
2. **非零退出。** 失败退非零，成功退 0。不靠输出里的关键词判断成败，不在失败时仍然退 0 打印警告——警告等于没有门禁。
3. **错误信息可执行。** 输出必须包含：违规的**文件与位置**、违规的**具体内容**、**期望形态**。人和 agent 读完就知道改哪里，不需要去读门禁源码。
4. **无副作用**（除了显式的 `--fix` / `--write` 模式）。默认只读。CI 里跑的一定是只读模式。
5. **确定性。** 同样输入同样结果，不依赖时间、网络、机器上的可选工具、文件系统遍历顺序。需要可选外部工具时，缺失就**明确跳过并说明**，不要假装通过。
6. **声明它消费源码还是构建产物。** 消费构建产物的门禁必须显式声明这个依赖，且不能在干净检出上直接跑（要先构建）。两个平面不能混：静态门禁解析源码，产物门禁读构建输出。
7. **自证。** 见下一节。

另外两条工程性要求：路径处理跨平台（分隔符归一化在门禁入口处做一次），平台适配留在拥有它的那个门禁里，不要为此建一层共享"平台层"。

## 门禁自证：门禁必须证明它会拒绝

**"在真仓库上跑通了"不是自证。** 那只证明当前仓库合法。一个写错了正则、永远匹配不到任何东西的门禁，在真仓库上永远是绿的，并且提供比没有门禁更危险的虚假安全感。

每个非平凡门禁必须有一个测试，做三件事：

1. 构造**合成的非法输入**（临时目录里的最小 fixture、内存字符串、假的包结构）。
2. 对它跑门禁逻辑。
3. 断言**失败**，并断言**错误信息**包含定位与原因。

同时至少构造一个**合法**输入断言通过，防止门禁变成"永远失败"。

纪律：

- **每一条新增或修改的接受/拒绝规则，都要有一个对应的非法样例证明它被拒绝。** 加了新规则却没加对应的拒绝样例，等于这条规则没有生效证据。
- 自证测试断言的是**门禁逻辑**，不是真仓库状态。不要写"跑一遍真仓库应该通过"的测试——它会在任何无关改动上失败，且证明不了拒绝能力。
- 复杂门禁（解析、图分析、组合规则）优先用**基于属性的测试**：生成一族输入，断言不变量。
- 门禁的自证测试与其他测试同层归属（见 [evidence.md](evidence.md)），跟着门禁源码走。

## 编排

门禁数量一多就必须有编排器，否则没人知道有哪些门禁、该跑哪些。

- **一个权威清单**：一份源码（脚本或配置）列出全部门禁及其分组，**它是门禁清单的唯一归属**。文档里不手抄门禁列表——手抄的清单一定会漂移；文档链接到这份源码。
- **分组按用途**，不按技术：本地精选组（改了文档跑哪些、改了包结构跑哪些）、CI 全量组、需要构建产物的组、需要凭证的组。
- **可单独跑**：任何一个门禁都能单独一条命令跑起来。编排器不能是唯一入口，否则调试一个失败要跑全套。
- **失败聚合**：一次跑多个门禁时，收集全部失败再统一报告，而不是首个失败即中止——否则修一个跑一遍，反馈周期被人为放大。
- 门禁调用包管理器/子进程时不经 shell（避免引号与转义问题）。

## 生成物防漂移

任何生成的产物（文档、目录、代码、依赖清单、图表）都必须有生成器 + `--check` 双模式：

- **生成模式**：写入文件。
- **`--check` 模式**：在内存里生成 → 读已提交文件 → **逐字节比较** → 不一致即非零退出，并提示"运行 `<生成命令>` 重新生成"。

三条硬性要求：

1. **生成器必须确定性、幂等。** 排序稳定、不含时间戳、不含绝对路径、不含随机 id。做不到确定性的生成物无法被门禁守护，等于不受控。
2. **手改生成物一律禁止。** 文件头写明"由 `<命令>` 生成，请勿手动编辑"。发现需要手改，说明生成器缺能力——改生成器。
3. **`--check` 进 CI 门禁组**，且属于"文档类改动"的本地精选组。

这个模式的价值是把"忘记重新生成"从一类反复发生的低级错误变成不可能：源码变了但生成物没跟上，CI 立刻红。

## 值得优先建的门禁

不分技术栈，按性价比排序。**从第 1 条开始，一次只加一个。**

| 优先级 | 不变量 | 为什么值 |
|--------|--------|---------|
| 1 | 文档里的相对链接/引用全部可达 | 极便宜、语言中立、立刻抓到真问题；还能顺带验证整条门禁通路是否打通 |
| 2 | 生成物新鲜度（`--check`） | 把最常见的"忘了重新生成"直接消灭 |
| 3 | 决策记录格式与分类合法（状态与目录互为校验、必需章节存在） | 决策记录一旦允许自由格式，半年内会退化成随笔 |
| 4 | 包/模块清单一致性（依赖声明、导出映射、入口存在） | 破损的清单在发布时才暴露，代价最高 |
| 5 | 源码注释里引用的文档路径可达 | 代码里的失效链接没人会发现 |
| 6 | 文档里粘贴的类型/接口与源码一致 | 粘贴的示例一旦漂移，比没有示例更有害 |
| 7 | 公开导出必须有文档注释（含参数与返回） | 契约缺失在评审里很难被系统性发现 |
| 8 | 构建产物可被外部消费者正常解析与运行 | 只有跑真产物才能暴露被开发期工具链掩盖的问题 |
| 9 | 字数预算 | 见 [standing-orders.md](standing-orders.md)，L3 才装 |

同样有价值但只在对应条件下装：单仓多包的依赖图/分层约束、供应商代码（vendored）改动与其清单同步、双语文档配对、死代码与重复代码检测、发布前的最小依赖发布间隔策略。

## 不该做的

- **禁止用 lint 全局关闭来绕过一条规则。** 需要例外时用最窄的、带理由的局部豁免。
- **禁止为了让 CI 变绿而放宽门禁。** 抬阈值、加豁免、跳过检查都必须是独立且有理由的决定并被记录。**安全相关配置与发布策略配置永远不允许为此修改**——升级给人类。
- **禁止空壳门禁。** 项目里不存在该类对象时不要装对应门禁；它永远不会失败，只会训练所有人忽略门禁输出。
- **禁止让门禁承担判断题。** 机械可查的进门禁；需要语义判断的（设计是否合理、抽象是否恰当）写进评审标准，并要求判断者产出结论 + 依据 + 证据路径。把判断题硬塞给门禁，结果是门禁被绕过或被削弱成无意义。
