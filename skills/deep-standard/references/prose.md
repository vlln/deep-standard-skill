# 散文即契约

适用范围：Markdown 文档、API 文档注释、代码与测试注释、提示词、命令与参数描述、诊断与错误信息、CLI/UI 文案。**长度本身从不是缺陷**——判据是它承载的是契约还是转录。

## 契约 vs 转录

**保留**（代码表达不了、但影响正确使用的）：

- **行为**：它做什么，在什么前提下
- **时序与模态**：同步还是异步、什么时候生效、能否重入、调用顺序要求
- **异常与失败**：会抛什么、什么条件下失败、失败后处于什么状态
- **后果**：调用它会改变什么，谁会观察到
- **所有权**：谁负责创建、谁负责释放、谁是权威来源
- **安全使用条件**：并发约束、资源上限、不可重复调用之类
- **非显然的定位**：为什么这里必须是这样（一句话 + 链接到拥有理由的决策记录）

**删除**（推理转录）：

- 实现过程叙述（"首先我们……然后……"）
- 显然分支的证明
- 测试走查（注释里逐行解释测试在干什么）
- 评审历史与来回讨论
- 被否决的局部方案（属于决策记录）
- **代码复述**（`// 把 count 加一` 之类）

一条判定法则：**注释描述代码无法表达的契约或理由；它不复述代码已经隐含的东西。**

理由只写在**拥有它的那个位置**（接口定义处、共享的辅助函数处），不要在并列的每个实现旁边各抄一遍。

## 只写当前态

- 避免"以前 / 现在 / 不再 / 曾经 / 已重命名 / 被移动了"。**直接命名活着的机制。**
- 长期散文里不出现 PR 号、commit 哈希、分支/栈位置。
- 变更故事的家是：commit message、PR 描述、决策记录、事故复盘。

原因很直接：状态叙述会腐烂，而且读者要的是"现在是什么"，不是"经历了什么"。

## 必须有文档的地方

- **每个模块与每个公开导出**要有简洁的文档注释说明它非显然的契约；函数类的导出包含参数与返回值说明。这条应当由门禁强制（见 [gates-as-code.md](gates-as-code.md)）。
- 继承/实现声明的成员、协议槽位、构造函数，把文档留在**声明契约的那一处**（接口/协议/基类），不在每个实现处重复。
- **空的异常捕获必须写明它吞掉了什么、以及为什么不会有别的东西到达这里**，并且 `try` 块只包一条语句。
- 每个残留的类型逃逸（`any` 之类）要写明为什么无法用更窄的类型。
- 待办标记按紧急度分三级，选对级别，让扫代码的人能一眼分清发布阻塞项和"哪天再说"：
  - `FIXME` — 应当阻塞发布的问题
  - `TODO` — 有资源就该尽快修
  - `XXX` — 也许哪天会修，最低优先级，无承诺

## 机械可查的部分要接进门禁

一条可机械校验的散文规则如果没有门禁，就等于不存在。至少接进去这些：链接可达性、导出文档注释完整性、文档里粘贴的类型与源码一致、（L3）字数预算。并且每条新增或修改的接受规则，都要有一个非法样例证明它被拒绝。

需要语义判断的部分（这段是契约还是转录）写进评审标准，要求判断者产出**结论 + 依据 + 证据路径**。

## slop 清单

审计任何文档都过一遍这张清单：

- **同一条规则有两个以上的家。** 搜一个特征短语；留一个家，其余改成链接。
- **叙述式历史与战斗故事**："以前""现在""不再""曾经""被重命名""被移动"、PR、commit。改成当前事实；需要时链接决策记录或事故复盘。
- **实现状态标注**："已实现！""未来会……""TODO: 待迁移"出现在散文或图里。状态会腐烂；目录结构与清单文件才是状态的权威。
- **手抄的目录/清单/枚举**：测试列表、模块列表、门禁列表、API 列表——只要源码或生成器是权威，手抄的一定漂移。
- **推理转录**：实现过程叙述、显然分支的证明、测试走查、被否决的局部方案。留下结果契约与长期理由，删掉推导路径。
- **理由抄在并列成员旁边**，而不是在拥有它的那一处写一遍。
- **段落墙**：一段里塞了好几条规则加括注补充。拆开，或把细节降级到它的家。
- **强调通胀**：加粗、全大写、"至关重要"到处都是就等于没有重点。**只给真正改变行为的那个从句留强调。**
- **已实施记录里的规划语气**："应该""待迁移""验收标准"。已实施的记录只描述现在是什么。
- **空壳章节**：标题存在但内容是"暂无"/"待补充"。要么写，要么删掉标题。

## 写作风格

- 读者是专业程序员。**简洁直白优于比喻。**
- 不要滥用某几个抽象名词（"缝""表面""词汇""门禁"之类）——一个词到处用就失去区分度。
- 段落排版遵循项目的机械规则（例如"一段一物理行、靠编辑器软换行"），代码块、表格、列表结构保持自己的格式；代码注释遵守 linter 的列宽。
- 跨引用**一律用可机械校验的相对路径链接**，绝不用裸文件名、编号或纯散文描述。注意链接检查通常只校验文件存在、不校验锚点，锚点要自己核。
- 双语/多语项目：任一侧的改动都同时义务化另一侧，并在同一个改动内完成。
