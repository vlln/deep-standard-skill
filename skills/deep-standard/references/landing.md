# 落地纪律

## 一个 PR 一种性质

每个 PR 恰好一种性质（`feature` / `bug-fix` / `doc` / `testing` / `cleanup`），加上对应的范围标签。分类集合是可扩展的，但**扩展是一次被记录的决定**，不是随手加标签。

- **独立的改动拆开。** 混装的 PR 无法被单独回滚、单独评审、单独归因。
- 标签不是装饰：它决定评审者用哪套标准看这个 diff，也决定发布说明怎么归类。
- 顺带修掉的无关问题 → 单独 PR。除非它小到"不修就没法完成本 PR"，且在描述里点明。

## 在引入处修

**发现一个缺陷源于某个尚未落地的 PR，就去那个 PR 上修，而不是在下游 PR 里打补丁。**

理由：在下游修会让引入的那个 PR 带着已知缺陷进入历史，且两个 PR 的评审者都看不到完整图景。下游打补丁还会在依赖链上不断传播——每一层都要重新解决同一个问题。

## 依赖链

- 有依赖关系的 PR 链，用**平台官方的栈机制**（GitHub stacked PRs 或等价物），让平台拥有栈范围的规则、CI、顺序、retarget 与合并状态。
- **不要用"手工合并 + 改 base"复刻栈语义**：手工复刻会在中途状态下丢失顺序保证，且没人能看出真实的依赖关系。
- 官方栈能力不可用时**硬停**，不要退回手工流程；跨 fork 的依赖链同样硬停（栈通常要求所有分支在同一仓库）。
- 独立 PR 与官方栈都可以在评审后 merge-forward 或 rebase；选择哪种是有意识的决定，写在 PR 里。

## 历史重写

- 只用 `--force-with-lease`，远端有移动就**中止**，永不裸 `--force`。
- 进行中的 merge-forward 在取用更新的 base 之前，先保住它的检查点。
- 不改 git 配置，不用交互式（`-i`）操作。

## 推送与合并前

1. 确认检出与分支。
2. 检查出站 diff 触达了哪些表面。
3. 按 [evidence.md](evidence.md) 选**最小充分证据**并跑一次。**只汇报真正跑过的命令。**
4. 若使用官方栈的同步命令发布了级联 rebase：**立刻验证被改写的层**，验证通过前不合并。

**未被明确要求时不推送、不合并、不发布。** 不可逆或高成本的动作（合并到主干、生产部署、打版本 tag、发布制品、发邮件、调用有真实副作用的 API）必须获得人类**针对该具体动作**的显式批准；之前的批准不自动延伸到新的动作。

请求批准时给**决策简报**，不是执行日志：证据留在文档/PR/测试输出里，简报只引用路径；agent 已确认无问题的项一行汇总，只展开有风险的、需要取舍的、以及自己拿不准的；每个待定点附建议答案与理由，让人类可以只回"按建议走"。

## PR 描述

- 说清**为什么**，而不是复述**改了什么**（diff 已经说了改了什么）。
- 链接到本次改动新增或更新的决策记录。
- 列出真正跑过的证据（命令 + 结果），不要列没跑过的。
- 改了过时的行为并连带改了它的测试时，**在 PR 里说明为什么**这个行为过时了（元法则 A 的要求）。
- 抬了字数上限、加了门禁豁免、跳过了检查——**在 PR 里为每一项给理由**，不要混在功能改动里悄悄过去。

## Commit

- 提交信息聚焦"为什么"。
- 提交前检查是否含敏感信息。
- pre-commit hook 修改了文件导致提交失败时，把被修改的文件加入暂存区后重试；**不要用绕过 hook 的方式提交**。
- 没有改动就不要制造空提交。
